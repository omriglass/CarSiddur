## 1. What was measured (debug copy of production, pulled 2026-11-11 20:25 UTC, production's migration level)

- Planning one query on `v_board_rides` allocates **24.6 MB** and takes 17 ms (16.4 MB / 12 ms without
  RLS). The view is ~30 nested wrapper layers (one per migration that added a column), 464 lines.
- The plan is rebuilt on every call and the freed memory stays with the connection. Plateau per
  connection: `my_upcoming_rides` **53 MB** (output 18 KB), `week_board_rides` **34 MB** (output 252 KB),
  `merge_preview` 10 MB, others 4–7 MB; an idle connection is 3.3 MB. Live Postgres caches are only 7–9 MB.
- Through the real app (two Sadranim, board + siddur + /my a few times): 6 API connections, 49–70 MB
  each, 322 MB and rising. Production has ~11 API connections on a 1.42 GB machine.
- JIT is not involved. Ride count does not matter (205 rides cost the same as 110).
- **A ride's row is the same for every viewer.** For week 2026-11-08 (live) all 38 non-admin members got
  99 of 99 rows byte-identical to the unrestricted rows; for week 2026-11-15 (partly published) 35
  members got 44 rows, all identical, and the 3 Sadranim all 89. Only *which rides* a viewer gets differs
  (`rides_select`: manager of the week → all; otherwise non-draft rides on public days).
- Production's temp files (822 MB) come only from `scripts/perf/snapshot.sql`, not from the app.

## 2. Principle: no cache unless a measurement forces one

The cost is planning complexity, not computing the rows. So the first fix is a **rewrite with identical
output**, read fresh from the tables on every call exactly as today. No stored copy, no expiry time,
nothing new in the browser. What people see and when they see it does not change.

A stored copy (stage C) is built only if stage A misses its target, and then only in a form that cannot
drift (see §5).

## 3. Stage A — one light row builder (items 2 and 3)

**A0. Spike with a go/no-go number (half a day, debug copy only).**
Write `board_rows(p_department_id, p_week_start, p_ride_ids)` as a plpgsql `SECURITY DEFINER` function
made of several small statements (base rides → served → people → series/relay → routes → assemble),
returning `SETOF v_board_rides` so `types.ts` and the client do not change. Target: a fresh connection
stays **under 10 MB** after 12 calls and output equals the view's for every ride of every loaded week.
If the target is missed, stop and go to stage C.

**A0 result (§3a, debug copy, fresh connection, 12 calls as a member).** Spike (removed once the real migration `20261111110000` replaced it; in git history at 2064d5c)
(`pf1.board_rows(p_ride_ids)`, 11 small statements, ids only — callers pick the rides).
- Memory: 5 rides via the view 62 MB → builder **14.8 MB**; a whole week (99 rides) via `week_board_rides` 48.6 MB →
  **19.3 MB**. Target of 10 MB missed. Per statement: everything except the route is ≤ 9 MB (live caches alone are
  ~7 MB); the existing `ride_routes_json` adds 2 MB (5 rides) to 6 MB (99 rides), `request_stops_with_eta` 2 MB.
- Output: identical to `week_board_rides_rows` for all 288 rides of the three loaded weeks; identical to the view
  under RLS for every member (39 × 3 weeks), except the order of two same-instant `ride_passengers` rows (the
  builder uses the week reader's `created_at, id` tie-break).
- Found: `people[].leg` is null for a viewer outside the department, and nested rows for such a viewer go through
  RLS. A1: a caller who is not a member of the ride's department (nor admin/service) keeps the old view path.
- Next lever if needed: make `ride_routes_json` lighter (A4).

**A1. Access rule, once per call.** The builder decides visibility itself, with the same predicates
as `rides_select`: `can_manage_week(dept, week)` → every ride; otherwise `is_approved()` and
`status <> 'draft'` and `is_day_public(dept, week, day)`. Nested rows are read without RLS — valid
because of the "same row for every viewer" finding, and pinned by the oracle below.

**As built (A1/A2):** `board_rows(p_ride_ids)` takes ids only and returns nothing for a ride outside the caller's departments (those readers keep the view). The oracle is `supabase/tests/_board_rows_oracle.sql`, a script the runner appends to every suite before its rollback (no function in the schema); `passengers`/`served` are compared as sets plus `served`'s role/name order, because the view's order is open on equal timestamps.

**A2. The oracle (the regression control).** `v_board_rides` stays in the schema, unused by the app,
as the reference. `board_rows_check(dept, week)` returns the rides whose builder row ≠ view row for
the current viewer.
- `scripts/test-db.mjs`: after every SQL suite, before its rollback, run the check as service, a
  Sadran and a member for every week the suite touched — all 54 suites become coverage for it.
- A one-off script on the debug copy: every member × every loaded week (`load --all`), zero differences.
- `department_isolation.sql` classifies the new function; `rls_smoke.sql` grant test.
- Rule for later changes: a new column is added to the view and the builder in the same migration;
  the oracle fails otherwise.

**A3. Switch readers one at a time, smallest audience first, each its own commit and release:**
1. `my_upcoming_rides` (item 2) — finds the ride ids as today, then calls the builder.
2. The single-ride and subset reads (`week_board_rides_subset`, `siddur/api.ts` `.from("v_board_rides")`
   at lines 67 and 213 → RPC).
3. `week_board_rides` for members, then for managers (`week_board_rides_managed`).
Each step: `npm run check`, `db:test` with the oracle, `QA_API=1` API tests, the relevant Playwright
specs (`npm run impact`), and the memory measurement of §1 repeated.

**A4. Same treatment where the measurement says so:** `v_ride_car_neighbours`, `v_my_requests`,
`v_car_locations` were not measured for planning memory yet; measure in A0, fix only those above ~5 MB.

**A4 result (§3b, 2026-11-12).**
- `swap_day_cars` and `_day_car_swap_overlap_blockers` were the last code planning `v_board_rides`; one swap left ~25 MB
  with its connection. They read `_board_rows_build(ids, leg_depts)` now (the builder without the access rule, internal);
  `board_rows` = access rule + that. Nothing in the app plans the view any more except for a viewer outside the department.
- Measured as the app queries them: `v_ride_car_neighbours` 12 MB (6 rides) – 17 MB (a week), `v_car_locations` 7 MB,
  `v_waitlist_groups` 5 MB — all under the builder's 20 MB, so left alone. `v_my_requests` costs 52 MB but nothing reads it.
- Where a connection's 20 MB is after week reads: 3.3 MB the idle process, 9 MB live Postgres caches (catalog 2 MB, 182

Rollback: each reader is one `create or replace` back to the previous body (kept as
`supabase/rollback/<ts>_down.sql`).

## 4. Stage B — merge preview without writes (item 4)

**B1. Read-only seat check.** `ride_seats_verdict(ride, extra)` computes the same sums as
`assert_ride_seats_fit` over the ride's current `ride_requests` plus the proposed guests (leg →
out/return coverage derived in the function), returning the error code instead of raising.
`_merge_check` calls it in place of the delete/insert/raise probe. The real write in create/apply still
runs `assert_ride_seats_fit` — it stays the authority.
- Parity test: for every ride × request × leg of the copy's weeks (23,106 cases last time), the new
  verdict = the old probe's verdict; the same comparison on fixtures in `merge_verdict` SQL suites.
- Acceptance: `merge_preview` writes 0 WAL (`pg_stat_statements.wal_bytes`) and takes no row locks.

**B2. Fewer calls, still live.** One RPC `merge_previews(specs)` answers all legs of the popup and all
open merges of the board in one call (no parallel fan-out, so no self-deadlock). The board keeps asking
the server after a change — nothing is stored on the proposal, so nothing can go stale.

**B3. Double submits (DD1) and lock order** — unchanged from TODO PF1 causes 2–3: buttons disabled
while pending, idempotent `create_proposal`/send, one lock order (or an advisory lock per department
week) in the multi-row board RPCs.

B1 is independent of stage A and can go first.

## 5. Stage C — stored rows, only if A0 fails

One table `ride_board_rows(ride_id, row jsonb, built_seq)`, one row per ride, the same for everyone.
- **Validity comes from the existing change counter** (`week_change_seq`, bumped in the writer's own
  transaction by the `wcs_*` triggers that liveSync already relies on). A reader compares the week's
  counter with the stored one; equal → serve, different → rebuild that week under an advisory lock,
  then serve. No time-based expiry, no per-user copy, so two people can never be served different
  versions of a committed state.
- Names that the counters do not cover (profiles, destinations, children, ride types) get counter
  triggers first.
- `board_rows_check` runs in `npm run health` and in `app.tick()` for the live and next week; a
  mismatch repairs the row and is logged. A switch in `app_settings` returns readers to the direct path.
- Shipped in shadow mode first (written and checked, not read) for one week.

- Production's actual pool size was not read (the ~11 is from `pg_stat_activity` on 2026-11-07).
- The "same row for every viewer" finding rests on two weeks of real data; the oracle in every suite is
  what makes it a guarantee. If a case turns up where a member rightly sees less inside a ride, the
  builder gets a second, public variant of that field — still not a per-user copy.
- Whether a multi-statement builder reaches the 10 MB target is unknown until A0.

## 8. B4 — the week lock in every writer (planned 2026-11-12, **not started**; owner: performance first)

B3's lock covers the board's proposal writes only. The deadlocks seen in production (merge-preview probe, double
submits) are fixed; what remains is two different writers of one week locking its rows in a different order.

- **Rule:** every top-level function that writes a week's `rides` / `ride_requests` / `requests` / `proposals` takes
  `_board_week_lock(dept, week)` as its first statement, before reading any row it will change, then re-reads. A
  function that also runs inside another writer may take it too (the lock is re-entrant in one transaction) only
  when every top-level caller already holds it — otherwise it would wait while holding row locks.
- **Two weeks at once** (a series over a week boundary, `submit_series_request`, `shorten_series`): both locks, in
  date order.
- **Steps:** (1) list every writer from `schema-current.sql` (browser-granted RPCs, `app.tick()` steps, functions the
  edge functions call) and mark each top-level / nested; (2) board moves first (`edit_ride`, placement, swap, solver
  apply, cancel, driver, passengers), one migration; (3) members' writes (`submit_request`, withdraw, join, waitlist
  group), one migration; (4) a test that fails when a new writer is not classified (like `department_isolation.sql`).
- **Checks:** suites + oracle; `scripts/qa/race.mjs` pairs (two Sadranim, Sadran × member) with
  `pg_stat_database.deadlocks` unchanged; time `apply_solver_result` and `publish_siddur` — while they run, other
  writers of that week wait.
- **Not covered:** rows that are not per week (cars, profiles, settings).

## 9. Final measurement (2026-11-12, debug copy, database container capped at 1.4 GB and 1 CPU)

API-level load for 150 s: 2 Sadranim (week read, 12 merge previews in one call, the same draft created twice and
discarded, every ~0.4 s) + 10 members (`my_upcoming_rides`, `week_board_rides`, `week_change_seqs` every ~1.25 s).
- **Memory:** 10 API connections at **26–34 MB** each (before: 49–70 MB) — above the 20 MB of the week reads alone,
  because one connection also keeps the plans of the merge check and the proposal writers. Container 530 MB of 1.4 GB.
- **Times (p50 / p95):** week read 47–75 / 172–270 ms, 12 merge previews 140 / 393 ms, create draft 17 / 97 ms,
  discard 6 / 77 ms. Highest single call 1.4 s. No statement timeout, **0 deadlocks**, 0 temp bytes.
- **5 Sadranim** on the same drafts for 60 s (uncapped): 2,164 creates, 0 deadlocks, no draft left behind, no duplicate.
- Refusals seen: `seat_config_violation` (7 of ~3,600 creates, not investigated) and `proposal_not_draft` on a
  discard (3; another Sadran's draft had replaced it).
- Full Playwright on the disposable stack: 211 passed, 3 skipped, 1 flaky (`themes.spec.ts` network-idle timeout,
  passed on retry, ran while the 5-Sadranim load was on the same machine).
- Not measured: the browser itself, Realtime, board moves, solver apply, publish; absolute times on Supabase.
- `week_board_rides_managed` / `week_board_rides_rows` are no longer called by the app and still cost 34 MB — to drop.

### C2 — route hops priced once (2026-11-12, migration `20261112150000`)

After C1 was released (`v2026.11.12-2`), production's week read still took 1.7–5 s alone (EXPLAIN as a
Sadran, read-only) and touched 240,000–290,000 pages for ~100 rides. The three-week debug copy did not
show it; the full-history copy (`npm run debug -- load --all`) did. Cause: in `ride_routes_json` the `hop`
CTE ("once per pair") was inlined into its non-equi join with `seq`, so `place_travel()` ran for every
(route point × pair) combination — 22,480 calls for a 99-ride week. `hop as materialized` restores once
per pair.

| Week read, debug copy (full history) | Before | After |
|---|---|---|
| Pages touched | 201,000–240,000 | ~15,200 |
| Time | ~630 ms | 61–65 ms |

Every one of the 806 rides has an identical route before and after (md5 over `ride_routes_json`).
Lesson: profile on the full-history copy, with `pg_stat_statements.track = 'all'` to see nested statements.
