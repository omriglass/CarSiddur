# E2E audit — 2026-09-14

Full pass over all 27 `e2e/*.spec.ts` files against the current behaviour in `docs/REQUIREMENTS.md`
§13 items 77–85 and `docs/UX_FLOWS.md`, and against the actual code (components, RPCs, SQL guards)
where the docs left a question open. Scope: `e2e/**` only — no `src/` changes, no doc edits outside
this file, no Playwright run, no commit. `npx tsc --noEmit -p tsconfig.app.json` (e2e is included via
`tsconfig.app.json`'s `include`; there is no separate `e2e/tsconfig.json`) and `npx eslint e2e` both
pass clean after the edits below.

## Method

For each of the nine dated behaviour changes in the brief, I read the current component/RPC/SQL
implementing it, then grepped every spec for the Hebrew strings, testids, and RPC/table names that
change would touch. Two specs needed real fixture redesigns (found by reading the SQL guard behind
the known `board-coordination.spec.ts` failure and discovering the same defect independently in
`one-way-consent.spec.ts`); one needed flaky fixed-timeout waits replaced. Every other spec already
matches current behaviour — several (`multi-day.spec.ts`, `quick-one-way.spec.ts`,
`quick-request.spec.ts`, `board-mobile.spec.ts`) were evidently already updated the same day the
underlying behaviour changed.

## Known issue #1 — `board-coordination.spec.ts` (named in the brief)

Confirmed via `docs/TODO.md` "Flaky / time-dependent e2e specs" and the actual guard in
`supabase/migrations/20260910098000_reject_proposals_on_published_day.sql`: `create_proposal()`/
`send_proposal()` refuse a `created_via = 'sadran'` proposal whenever
`is_day_public(department_id, week_start, day)` is true (the day is in `weeks.published_days` of a
`published`/`live`/`archived` week) — the only exemption is `created_via = 'ask_to_join'`. The old
fixture called `publishedFixtureWeek(week)` (which publishes **all 7 days** by default,
`p_days default null`) before dragging a request onto a ride to compose a merge proposal on that
same now-public day — a deterministic `400 proposal_day_public`, not a flake.

Fix: the fixture no longer publishes at all. Every board/drag/edit action in this test goes through
the Sadran (`can_manage_week()`, which bypasses `is_day_public()` entirely), and the `/publish` page
visited mid-test is a **pre-publish readiness preview** — it was never actually being published in
this test, only previewed. So the week stays `solving` for the whole test.

## Known issue #2 — `one-way-consent.spec.ts` (found during this audit, not in the brief)

Same root cause, independently discovered while checking every spec that calls `create_proposal`/
`send_proposal`: this spec also calls `publishedFixtureWeek(week)` up front, then composes a
`created_via: 'sadran'` merge proposal on the same published week — this should fail identically to
issue #1 under the current schema. Unlike `board-coordination.spec.ts`, this test *does* legitimately
need the week published later on (a non-party, non-Sadran member must see the orphaned ride on the
public siddur to volunteer as its driver), so the fix reorders rather than removes publication: the
fixture builds the week as `solving`, negotiates the merge proposal and lets the driver cancel their
ride, and only then calls `publishedFixtureWeek(week)` — right before the step that actually needs
the day public — publishing the real, by-then-settled state instead of an empty week.

I could not run Playwright to confirm this was actually failing before my fix (out of scope per the
brief) — the diagnosis rests on reading the SQL guard and the RPC call it gates, not on an observed
failure. Worth a real run to confirm once the owner is ready.

## Flaky fixed timeouts — `board.spec.ts` (named in the brief)

Two tests (`"drag-drop: dragging an unmet round-trip request onto a car column creates a ride
there"` and `"bug #2: moving a ride to another car via the sheet's car selector persists"`) both
relied on a blind `page.waitForTimeout(300)` after clicking a day-tab radio, before reading board
state that depends on that day having actually rendered. Replaced with `expect(radio).toHaveAttribute
("aria-checked", "true")`, a real signal the click took effect. `selectDayFor` (shared by several
tests) got the same fix. Also replaced `bug #5`'s `page.waitForTimeout(2000)` after "auto-solve
remaining" with `page.waitForResponse(...apply_solver_result...)` (the same pattern already used by
this file's own `fillRemaining()` helper), for consistency — not one of the two tests named in the
brief, but the same class of fragility.
