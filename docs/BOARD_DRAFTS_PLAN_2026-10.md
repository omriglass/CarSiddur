# Board drafts, merged rides as one ride, ride-detail edits, manual handover — implementation plan (2026-10-05)

Spec of record: **REQUIREMENTS §13.94**; owner answers in `docs/TODO.md` "Owner feedback 2026-10-05" (G7–G10, Q1–Q5). This file fixes the cross-layer decisions so the SQL, board and solver-bridge steps agree. Each step updates DATA_MODEL / UX_FLOWS / SOLVER in the same change.

## 0. What exists (do not reuse for drafts)
- `rides.status = 'draft'` means "on a day not yet published" — every ride of an unpublished day is `draft`; members never see it.
- `rides.planning_conflict` = an overlapping ride the Sadran kept on an unpublished day (collision navigator, red stripes).
- `ride_change_requests.is_planning` = a Sadran's private shadow edit of a **published** ride (members keep the original); it blocks publishing.
- `proposals.status = 'draft'` today exists only transiently (the composer creates and immediately sends; a draft survives only when the send fails).
- `create_proposal` refuses public days (`proposal_day_public`): suggestions — and therefore drafts — only exist for unpublished days. Published-day edits keep using planning shadows.

## 1. Drafts (G9) = unsent proposals, shown on the board as an overlay
- A **draft is a `proposals` row with `status = 'draft'`** (any type: `shift`, `merge`, `origin`, and the ride-detail change of §3). No new table, no new status. A send failure that leaves a draft behaves exactly like an intentional draft.
- **Creating:** every board popup that leads to the composer (`MergePrefillDialog`, the drag-beyond-flexibility shift, suggestion "הצע" actions, the ride-sheet beyond-flexibility save, the new ride-detail edit) gets a **"טיוטה"** button next to "הכן הצעה": it calls `create_proposal` with the same payload the composer would build and returns to the board — nothing is sent. The composer itself also gets "שמור כטיוטה" beside "שלח".
- **Board rendering** (Sadranim only — members never see proposals that are not addressed to them, and never a draft): a draft is drawn as the **result** it would produce, with a dashed outline and a "טיוטה" tag: a `shift` draft → its request's ride at the proposed car/time (the original ride or unmet card is hidden); a `merge` draft → the merged ride (§2); an `origin` draft → the request placed on the proposed car from the proposed place. Tapping a draft opens a small sheet: **שלח** (opens the composer on that draft; sending = existing `send_proposal`), **ערוך** (composer), **מחק טיוטה** (discard). A **sent** proposal keeps today's pending-consent rendering, but merges render as the merged ride too (§2) — never as overlapping blocks.
- **New RPCs:** `discard_proposal(p_proposal_id uuid)` — Sadran (`can_manage_week`) only, `draft` → `withdrawn` (the status guard restores the request's previous status); `withdraw_proposal(p_proposal_id uuid)` — Sadran only, `sent`/`accepted` → `withdrawn`, tokens revoked, the member gets no new message (their inbox item disappears per G5). Both department-isolated (add to `department_isolation.sql`).
- **Solver / auto-fill:** a request that has a `draft` (or `sent`/`accepted`) proposal is left alone (not re-solved — today only `proposed` is excluded); the draft's resulting window is a **fixed block** on its car for the solver (so auto-fill does not put someone else there). `apply_solver_result` full mode keeps the host ride of a draft/sent merge (treat it like a pinned ride) instead of withdrawing the proposal.
- **Publishing is refused while drafts remain:** `publication_readiness` gains `draftProposals` per day; `publish_siddur` raises `publication_drafts` for any selected day with drafts, **not** bypassable by `p_allow_unanswered`; the publish screen lists the drafts (who, what, which day) with links back to the board and disables those days.

## 2. Merging makes one ride (G10)
- **Popup** (replaces today's `MergePrefillDialog` content): base = the ride dropped onto; the added request's name and route; **"הלוך בלבד" / "הלוך וחזור"** for the added person (→ merge legs `out` or `both`; for a request that is itself one-leg the choice is preset and hidden); the estimated time at their stop and, when it differs from their requested time, "השעה תשתנה ל-HH:MM"; buttons **טיוטה** / **הכן הצעה** / ביטול.
- **Route of a ride** (one definition per side — SQL `ride_route(p_ride_id)` and a pure TS twin used by the board for pending merges): the base request's route (its origin, stops, destination, and for a round trip its return route) with each added passenger's **boarding place** (their origin, if not already on the route) and **alighting place** (their destination) inserted where it adds the least driving (cheapest insertion over `place_travel`, keeping each passenger's boarding before alighting; both-ways passengers are inserted on the return route mirrored); estimated times along it (`stop_minutes` per stop). The merged ride keeps the base ride's start; its end is extended only by the added driving (and never shortened).
- **Apply** (`apply_proposal` merge branch): as today the guest's own booking is cancelled (`MERGED_BY_CONSENT`) and the guest joins the host as `passenger` with the chosen legs; the host window becomes base start → base end + added driving; the request's stops are not edited — the ride route is derived. The guest's driver (if their request had a driving companion / they drove) is a passenger now.
- **Rendering:** a merged ride (applied, sent or draft) is **one** block on the base car: normal colours plus a small merged marker ("· מאוחד"); its label and the ride sheet show the route with the added stops and times. The guest's own ride/unmet card is hidden while a draft/sent merge exists. Merges must not produce `scanBoardConflicts` overlap flags (the guest's own booking is excluded from the scan while its merge is pending).
- **Unmerge by dragging the added person out:** the ride sheet / block lists the added person as a draggable chip. Dropping it on the unmet list or on another car: draft → discard; sent/accepted → withdraw; applied → new RPC `unmerge_request(p_ride_id uuid, p_request_id uuid, p_expected_version int)` (Sadran only): removes the guest's `ride_requests` row, shrinks the host window back to its base route, returns the guest request to `submitted` (unmet), notifies the guest (`outcome_changed`) — then, if dropped on a car, the normal placement path runs.
- **Built 2026-10-05:** the chip is drawn inside the merged block on the grid (applied, sent or draft) and dragged with a pointer (`GuestChips`); the ride sheet's "הוצא מהנסיעה" button is the fallback (phone list mode). Drop targets as above; dropping on a car/ride unmerges first, then runs the normal unmet placement/merge path (UX_FLOWS §4.2).
- Fix the suggestion-merge path to send the full payload (legs + combined window), like the drag path.

## 3. Ride-detail edits (G8)
- Ride sheet gets **"מסלול"**: start place, end place, stops per leg (same `DestinationCombobox` + chips as the request form).
- On a ride that serves a member's request: saving creates a **`shift` proposal** whose payload may now also carry `origin_id`/`origin_text`, `destination_id`/`destination_text`, `stops` (same shape as `submit_request`'s `stops`) — draftable like any proposal; `apply_proposal`'s shift branch updates the request's places/stops (through the same validation as `submit_request`) and re-places the ride. On the Sadran's own reservation (no served request): `edit_ride` accepts `origin_id`/`destination_id` directly (stops on reservations: not in this step).

## 4. Manual handover waives the turnaround (G7)
- When the Sadran **manually** places/moves/resizes a ride (board drag, ride sheet, unmet drop, applying a Sadran shift) so that it starts **at the place the car's previous ride ended, and that place is not the car's base**, the buffer between the two is waived: SQL `prepare_manual_ride_window` sets the previous ride's `turnaround_override_minutes` to the real gap (0 allowed) — as today — and the pair is **not** flagged as a tight schedule nor as a conflict on the board (`scanBoardConflicts`, `tightScheduleRideIds` skip such a handover pair). At the base, and for automatic placement (solver, auto-approve), the buffer still applies.
